# 0012. The product becomes Grumpo and blocks get a screen, with the app identity renamed and the daemon identity kept

Accepted on 2026-10-12. Amended the same day, when the app identity was renamed after all.

## Context

The owner gave the product a name and a character, Grumpo, a grumpy and loyal guardian whose tagline is "Grumpo says no. You get things done." The brand kit in `brand/` defines the mascot, the wordmark, the icon, the palette and the voice. Two questions followed from it. The first is which of the names in the system change, because Focus appears both in what a person reads, such as the window title and the notifications, and in identifiers that macOS and the installed daemon key their state on, namely the bundle id, the executable name, the daemon label and binary `focusd`, the socket, the state and log paths and the crate names. The second is what a person sees when enforcement quits an app or closes a tab, since a macOS notification in the corner is easy to dismiss and does little for a tool whose purpose is to make an impulsive decision cost something.

The first version of this decision kept every identifier, because changing one is expensive for a person who already has the app. macOS stores the Automation and Accessibility grants against the app's code signature and bundle id, the login item is a property list named after the label, the usage database and the logs live in folders named after the bundle id, and the daemon keeps its rules and unlock state under its own paths, so a rename of any of them would make a person grant the permissions again, lose the login item or lose their rules while the hosts block kept running without a way to edit it. That choice showed its cost at once. System Settings lists Accessibility and Automation grants and background items under the name and icon macOS recorded for the bundle id and the executable, so the owner saw an entry called Focus with the old blue icon under Privacy and Security, and one called focus-app under Background Activity, in an app that was otherwise called Grumpo everywhere. Those two places are where a person decides whether to trust the app, so a stale name there undoes the branding exactly where it matters. The daemon has no such exposure, since it is a system-level LaunchDaemon that no settings pane shows by that name and that the person never opens.

## Decision

The app's identity is renamed and the daemon's is kept. The bundle id becomes `io.github.brian-rey-development.grumpo` and the main executable is `Grumpo` through the Tauri `mainBinaryName`, next to the `productName` that already made the bundle `Grumpo.app`, so every system listing shows the name and the icon of the brand. The login item label follows the bundle id. The daemon label and binary `focusd`, the socket, the state and log paths, the `FOCUS_SIGNING_IDENTITY` variable and the crate names, including the Cargo binary `focus-app` that the bundler renames, stay as they were, because renaming them would strand the installed daemon and its state for a name nobody reads. The daemon accepts the renamed app without any change, since it authorizes a client by the uid of the socket peer and never by bundle id or path, and the one place in the code that listed the app's bundle id, the protected apps that can never be blocked, now holds both the new id and the earlier one, so a copy of the old app that was never removed stays unblockable too. The window, the tray, the notifications, the setup, the password prompt text and the documents say Grumpo, and the background service is called the Grumpo service in copy. Focus remains only as the concept, as in focus windows and "Focus on until {time}". The administrator prompt of [ADR 0011](0011-app-installs-the-service-through-the-admin-prompt.md) carries the text "Grumpo needs your password to install the service that blocks sites." through the `with prompt` clause of `do shell script`, which replaces the generic wording that names osascript.

The first start under the new identifier migrates what the old one left, in two independent steps that are safe to repeat. The app data folder, which Tauri names after the bundle id and which holds the usage database and the settings, is moved from `~/Library/Application Support/io.github.brian-rey-development.focus` to the folder of the new id with a single rename, which the file system applies completely or not at all, so a crash leaves the data in exactly one place and the SQLite files travel together. Nothing is moved when the old folder is missing, as on a fresh install, or when the new folder already holds data, in which case the old one is left alone. Nothing is moved either while the earlier app is running, which the app asks `NSRunningApplication` for by the old bundle id, because the old process keeps its database files open and would go on writing into the moved folder, so the new app uses the old folder for that run, logs it at info level and moves it at the next start when the old app is gone. If the question itself fails the move waits as well. While both apps run they share one database, so the time they both track is counted twice until the old one quits. If the rename is refused the app keeps using the old folder for that run and tries again at the next start, so a failure never hides the history behind an empty database. The login item is replaced by `sync_on_start`: when a property list under the old label, or under the even older label `Focus`, is found in `~/Library/LaunchAgents`, the item under the new label is enabled first and the old lists are deleted after, so a crash between the two leaves both and the next start finishes, whereas the other order could leave neither. A person who had launch at login off has no old list and gets no new item. Each step logs that it happened without paths above debug level. Nothing in the Mac's privacy database can be moved, so the Accessibility and Automation grants are asked for again under the new name and the README gives the `tccutil` command that clears the stale entries of the old one.

Blocks are shown on a block screen. When the executor quits a blocked app or closes a blocked tab it builds a `BlockScreen { target, reason, until, strict }` and hands it to a `BlockScreenHub`, which stores it as the current content and asks the `blocker` window to show it. The window is created on first use, reused afterwards and hidden when closed, so a second block while it is open replaces its content and windows never stack. The webview reads the content with `get_block_screen` when it starts, because a block can arrive before the page listens, and follows the `block-screen` event after that. `dismiss_block_screen` hides the window and gives focus back. Every show carries an increasing `id` that the hub stamps on the block, the page hands it back when it dismisses, and a dismissal for an id that is no longer current does nothing, so a click meant for an earlier block cannot swallow a newer one that arrived at the same moment. The content is stored in the hub and emitted to the page before the window is ordered front, so the first visible frame never shows the previous block, and the window is told with `block-screen-hidden` just before it hides so the page can start clean on the next show. The block notification stays as the fallback when the window cannot be shown, and the limit warning with 5 minutes left stays a notification, since it tells the person something before any block exists.

The contract is derived from what the daemon status and the policy already know and adds no field to the IPC protocol. The target is the covering rule for a site and the app name for an app. `until` is the end the policy already computed for the notification, which is the schedule window, the coming midnight for a spent limit, or nothing for a schedule with no end. The reason is `limit` for a target held only by a spent limit, `schedule` for a scheduled target, and `always` for a scheduled target whose block has no end. When a schedule and a spent limit hold the same target the reason is `schedule`, because the schedule decides when the block lifts. `strict` is true while enforcement is active and no unlock is running, which is when the daemon rejects a loosening, so it holds for every block the policy produces today and is kept in the contract so that a future mode with loosening allowed has a place to say so.

The enforcement worker never waits for the main thread, because the main thread joins that worker when the app exits, and building or showing a window waits for the main thread when it is called from another one. The surface therefore queues its work with `run_on_main_thread` and returns at once, and the fallback notification runs from the queued job when showing fails, which is the same arrangement the menu bar uses. The `blocker` window has its own capability file with the two block screen commands and the event listen permissions, so it cannot call any other command and cannot move itself.

## Consequences

A person upgrading keeps their rules, history, settings and login item through the migration, goes through the onboarding flow again because the new bundle id has no completed marker and macOS permissions must be granted again anyway, which is intended, and has to grant Accessibility and Automation again, because those grants belong to the bundle id and cannot be carried over. They also have to remove the old `/Applications/Focus.app` by hand or through the install command in the README, which deletes both names, and may clear its stale entries with `tccutil reset All io.github.brian-rey-development.focus`. Two copies would run two apps over one database, so the README says to quit Focus first, and the migration waits for a start when the old copy is gone. The product and the daemon now carry different names, so a contributor reading `focusd` or `~/Library/Logs/Focus` will meet the old word, and this record is where to find out that it is deliberate.

The block screen costs one more window, one more Vite entry and a second capability file, and it makes a failure to show the window a case that needs a fallback, with the price that the fallback is reported from the main thread and not synchronously to the policy. The policy still records the block as announced when the screen was queued, so a block whose window fails is announced by notification at most once a minute, as before, and a block whose queue fails is not retried until that minute has passed. The `skip_taskbar` option has no effect on macOS, where a second window never gets its own Dock tile or Cmd-Tab entry, so the requirement holds by construction.

If the person ever needs a mode in which blocks can be loosened without a cooldown, `strict` is already in the payload and the screen already renders the difference.
