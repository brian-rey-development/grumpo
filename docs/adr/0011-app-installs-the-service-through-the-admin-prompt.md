# 0011. The app installs the service through the administrator prompt

Accepted on 2026-10-12.

## Context

The privileged daemon described in [ADR 0002](0002-privileged-daemon-owns-rules.md) has to be installed by root, and until now that meant a person building the repository and running `sudo scripts/install.sh` in Terminal. Settings showed that command whenever the service was missing, which is acceptable for the developer who wrote it and wrong for anyone else, since installing or updating the service should take one click and the password prompt that every Mac user already knows.

Apple's intended mechanism for a daemon that ships inside an app is `SMAppService.daemon`, where the app bundles a launchd plist and asks the system to register it, and the person approves it once in System Settings under Login Items. It was rejected for now because Grumpo is signed ad hoc, as there is no Apple Developer identity on the machine that builds it, and Apple's developer technical support has said that ad hoc signed daemons registered this way lose their background permission across restarts, which would leave a person without enforcement after a reboot and without any visible cause. The older `SMJobBless` is deprecated and needs a Developer ID as well.

## Decision

`Grumpo.app` carries the daemon and the existing installer, and runs the installer as root through `/usr/bin/osascript` with `do shell script ... with administrator privileges`, which makes macOS show its standard password prompt. The bundle holds `Contents/MacOS/focusd`, signed before the app is sealed, and `Contents/Resources/installer/` with `scripts/install.sh`, `scripts/lib/` and `packaging/macos/`, which is the same relative layout as the repository so the script finds its helpers and templates without change. `scripts/build-release.sh` adds these files through a Tauri configuration overlay that only it passes, so `cargo test`, `tauri dev` and `scripts/check.sh` still work when the inputs do not exist, and it fails unless `codesign --verify --strict --deep` passes on the finished app and the bundled daemon keeps its own identifier and hardened runtime.

The backend exposes the `install_service` command, which takes no arguments and returns `installed` or `cancelled`, or fails with `serviceInstallUnavailable` when the installer is not bundled, as in a development build or on another system, or with `serviceInstallFailed` when it ran and failed. The command calls the `ServiceInstaller` port, implemented for macOS in `platform/macos/service_installer.rs`, and after a successful install it asks the daemon for its status at once, so the interface sees `connected` without waiting for the next poll.

The interface passes nothing, and the backend derives everything it needs. The installer and daemon paths come from `current_exe()`, which must sit in `Contents/MacOS` of a bundle that contains both files, and the owner is the uid of the app process, passed as `--owner` because `SUDO_USER` is not set under `osascript`. The AppleScript source is a fixed text that reads its values from `argv` and applies `quoted form of` to every one of them, so no path or name is ever interpolated into the script. What root runs first is not a file of the bundle but a fixed bootstrap in the app, started as `/usr/bin/env -i PATH=/usr/bin:/bin:/usr/sbin:/sbin HOME=/var/root /bin/bash --noprofile --norc -c <bootstrap>`, because `do shell script` passes the environment of the app on, and a `TMPDIR` or `BASH_ENV` set by another process of the user would otherwise reach a root shell. The bootstrap creates a folder with `mktemp -d /private/var/tmp/grumpo-install.XXXXXX` and mode 700, copies the installer folder and `focusd` into it with `cp -L` so that a link inside the bundle cannot point root at a file outside the copy, runs `codesign --verify --strict` on the copied daemon, and runs `install.sh` from the copy only, removing the folder when it ends. The installer renders the LaunchDaemon plist straight into `/Library/LaunchDaemons` with a restrictive umask and moves it into place, so nothing root writes goes through a folder the user owns, and it takes a lock in `/var/run` so that two installers cannot take each other's backups apart. The app also refuses a second install request while one runs, and when its wait for the prompt times out while the installer still holds its lock it reports `serviceInstallBusy` and not a failure, because the installer started as root keeps running after the app kills `osascript`. A dismissed prompt reports `-128` and maps to `cancelled`, which is an outcome and not an error, and any other non-zero exit maps to `serviceInstallFailed`. The log keeps a fixed sentence above debug level, and the tail of the installer output goes to debug with home folders blanked and never travels to the interface, which words every failure from the code alone.

The Terminal path stays as the alternative for developers, and the interface shows it when the installer is unavailable or after a failed attempt.

## Consequences

A person installs and updates the service from the app with one click and one password, and the app and the daemon it installs always come from the same build, which removes the version skew that the Terminal flow allowed. The cost is that root runs a script that began its life inside the app bundle, and the bundle belongs to the user. The copy into a root-owned folder closes the window between checking and using the files, and the signature check on the copied daemon catches damage. Neither authenticates the bundle, because the app is signed ad hoc and anyone can sign a file that way. So a process that already runs as the user can alter the installer or the daemon inside the bundle and re-sign it before the person types the password, and its code then runs as root. This is the same trust model as other installers that ask an ordinary, user-installed app for an administrator password, and it does not give that process anything it could not do as the user, such as replacing the app itself, but it does turn the password prompt into a way to reach root. The threat model lists it as an accepted gap, and ad hoc builds are for development and for people who accept it. The fix that closes it is a Developer ID signature, with which the bootstrap can require the team identifier in the requirement it checks on the copied daemon and on the bundle, or `SMAppService.daemon`, with which launchd checks the signature and the password script disappears.

The password prompt is shown by `osascript`, so its wording names that tool and not Grumpo, and a person who has never seen it may hesitate. The interface explains beforehand that macOS will ask for the Mac password once. Ad hoc signing also means every rebuild produces a new app and a new daemon, which the update path handles because it reinstalls both together.

This decision should be revisited when a Developer ID exists. At that point `SMAppService.daemon` becomes viable, gives a native approval flow with the right name on it, and removes the need to run a shell script as root, so a later record would supersede this one while keeping the `ServiceInstaller` port, which hides the mechanism from the rest of the app.
