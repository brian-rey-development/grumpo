# Threat model

Grumpo is a self-control tool. Its purpose is to make an impulsive decision more expensive than a deliberate one, and it is not a security boundary against someone who administers the machine. A person with `sudo` can stop the daemon, edit `/etc/hosts` or uninstall the app, and Grumpo does not pretend otherwise. What it does is raise the cost of the easy, in-the-moment bypass, such as editing a rule, closing the app or flipping a toggle, to a level where the pause itself gives the person time to reconsider.

## Assets

The assets worth protecting are small in number. The rules (blocked sites and apps, the schedule and the daily limits) express the person's intent and are what an impulsive decision would try to weaken. The unlock state records whether enforcement is currently relaxed and when it will relock, so forging it would be equivalent to bypassing the tool. The marked block in `/etc/hosts` is the actual enforcement mechanism for websites, and a corrupted hosts file would either fail to block or damage the person's unrelated entries. The usage history is the only sensitive personal data, and although it stores only app names, hosts and timestamps, it still reveals habits, so it is kept local and deletable as described in [privacy.md](privacy.md).

## Actors

The primary actor is the impulsive self, meaning the same person at a weaker moment, with full access to the user account and no wish to read documentation while bypassing a rule. Nearly every mitigation targets this actor, which is why the design leans on friction in the form of the escalating cooldown and the typed sentence from [ADR 0005](adr/0005-escalating-cooldown-and-typed-sentence.md), and on moving authority out of reach of the user session.

The second actor is another local process running as an unprivileged user, for example a script, a browser extension host or a compromised developer tool. It might try to talk to the daemon socket, to tamper with the state file or to feed the daemon crafted payloads. The design treats it as a realistic but low-powered adversary and constrains it with the controls below.

Malware with root, or a human with root, is out of scope. Anyone who can already write `/etc/hosts` or replace the daemon binary has the same power as the daemon, and no software running on that machine can defend the rules against them.

## Attack surfaces and mitigations

| Surface | Threat | Mitigation designed in |
|---|---|---|
| Daemon socket | A local process of another user, or a non-owner uid, issues requests | The listener checks the peer uid with `getpeereid` and serves only the owner uid configured at install time and root, as described in the section on the socket below |
| Daemon socket | Oversized or slow requests exhaust memory or hold connections | One request per connection, a two second budget to read the request and another to write the response, and a bounded frame reader with caps of 256 KiB for requests and 1 MiB for responses |
| State file | Another process edits rules or unlock state on disk | The file lives in a root-owned directory with mode `0600`, so only root can write it, and it is written atomically through a temporary file and rename |
| State file | A crash or corruption leaves a half-written file | Atomic writes and a `schemaVersion` with forward migrations. A file that is damaged, unversioned or holds rules that no longer validate is moved aside with a timestamp and the daemon starts from safe defaults, as described in the section on state that cannot be loaded below |
| State file | A read error or a newer file makes the daemon start with empty rules and switch enforcement off | Any load failure other than an unusable file makes the daemon exit with an error and leave the file in place, so launchd retries and the existing hosts block stays |
| State file | A failing or full disk is used to stop a new rule from taking effect | A change that only tightens enforcement is applied in memory even when it cannot be saved, and the save is retried on every reconciler tick, while a loosening or neutral change that cannot be saved is refused so that memory never runs ahead of disk in the permissive direction |
| Hosts file | Corrupting unrelated entries, or writing arbitrary lines | Only the marked block is replaced, domains are validated by the `Domain` type before rendering, writes happen only when content changes, and the write is atomic through the resolved symlink target |
| Hosts file | A site stays reachable through a common alias of its name | Each blocked domain is written for a fixed list of alias prefixes in IPv4 and IPv6, as described in the section on the hosts block below |
| IPC payloads | A malformed or hostile body reaches the rules engine | A version envelope that is checked before the body is parsed, `deny_unknown_fields` on rule payloads, and `ValidatedRules`, so unvalidated rules cannot reach persistence or enforcement code |
| Strictness | A compromised or buggy UI submits a loosening while enforcement is active, or raises a limit before it bites | The daemon computes the loosening itself from the old and new rules and rejects it with `loosening_locked`, so the app has no code path that skips the check. Raising or removing a daily limit is rejected unless an unlock is active, whatever the schedule, as [ADR 0010](adr/0010-raising-a-limit-always-needs-an-unlock.md) records |
| Rules | A rule blocks an app that Grumpo or the Mac needs in order to work, which would trap the person | Rule validation rejects protected apps with `rules_invalid`, as described in the section on protected apps below |
| Limit reports | A stale or forged report marks a target as spent | A report carries the allowance that ran out and the reporter's local day, and the daemon records it only for today and for a limit that still exists and is not higher than that allowance, otherwise it ignores the report, as described below |
| Clock | The system clock is set back to stretch an unlock or to get a fresh daily count | Phases that hold more time than they were granted are restarted or dropped, and day counters reset only when the date moves forward, as described in the section on the clock below |
| Browser automation | Injection through AppleScript arguments or page-controlled strings | Scripts are fixed text with one exception, the tab-close script, which embeds the observed tab address as an AppleScript string literal so that it can confirm the tab did not change before closing it. The address is capped in length, backslash, double quote, newline, carriage return and tab are escaped, any other control character makes the app skip the close instead of altering the value, and the script is passed to `osascript` as separate `-e` arguments without a shell. Every call has a timeout and a typed error, and the address that is read back is reduced to a normalized host immediately |
| Installer | The app runs a script as root, and the script lives in the app bundle, which sits in `/Applications` where the user's own processes can write | The app reaches the installer only through `current_exe()`, never through input from the UI, and passes its paths and the owner uid as arguments of a fixed AppleScript that applies `quoted form of` to each, so nothing is interpolated into script source. Root starts from an empty environment (`env -i` with a fixed `PATH` and `HOME`), so a `TMPDIR` or `BASH_ENV` of the app cannot reach it, and a fixed bootstrap copies the installer folder and `focusd` into a fresh folder under `/private/var/tmp` that only root can enter, follows links while copying so none can point outside, checks the copied daemon with `codesign --verify --strict`, and runs the installer from that copy only. The installer renders the LaunchDaemon plist directly into `/Library/LaunchDaemons`, and no file root writes passes through a folder the user owns. Only one installer runs at a time, through a lock root owns. The copy closes the window between checking the bundle and using it, and it does not authenticate the bundle, which the next section states. [ADR 0011](adr/0011-app-installs-the-service-through-the-admin-prompt.md) records the decision |
| Webview | Remote content or script injection into the UI | A content security policy with `default-src 'none'`, no remote origins, a UI that reaches the backend only through typed commands, and two capability files that grant the main window only event listening, window dragging and the app's own commands. The notification and autostart plugins are not exposed to it |

The common thread is that the daemon never trusts the app for policy decisions. The app can be replaced, patched or driven by another process running as the same user, so the daemon validates every rule set into a `ValidatedRules` value, computes strictness from first principles, and owns the clock-driven state transitions in its reconciler. This design is recorded in [ADR 0004](adr/0004-strictness-enforced-in-daemon.md).

## Who may talk to the socket

The peer check accepts two uids, the owner uid that `install.sh` passes to the daemon (the user who ran `sudo`, or the one named with `--owner`) and root, because root can already do everything the daemon can and refusing it would only break the installer, which pings the daemon as root to confirm that it started. Beyond that the check identifies a user and not a program, so any process running as the owner uid is treated like the app. That process can tighten the rules by adding sites or apps, extending the schedule, adding limits, relocking or reporting that a limit was reached, and the daemon accepts all of these because they only make enforcement stricter. It cannot loosen anything while enforcement is active, and it cannot raise or remove a daily limit at any time without an unlock, since the daemon computes loosenings itself and demands the unlock flow with its cooldown and typed sentence, which is the same friction the person faces, so a script gains no shortcut that the person lacks.

A limit report deserves a closer look, because the daemon cannot verify the usage behind it, which is stored in the app's database and not in the daemon. A process running as the owner can therefore report a limit as reached early and get a target blocked until midnight. The daemon accepts this on purpose. The report can only make enforcement stricter, so the worst outcome is that the person blocks their own site for a day, which is within their authority anyway, and verifying usage would require moving the usage database into the privileged side for no gain in protection against the impulsive self.

The daemon could narrow this further by asking the kernel for the peer's process id with `LOCAL_PEERPID` and verifying the code signature of that process with `SecCode`, so that only the Grumpo app qualifies instead of every process of the owner. That check needs a signing identity the daemon can pin, and the builds Grumpo ships are signed ad hoc or with a certificate the person made for themselves, with no Developer ID or notarization, so v1 does not do it. It would also complement the strictness rule without replacing it, since a signed app can still be driven by someone at the keyboard.

## Protected apps

A rule that blocks the wrong app does not raise the cost of an impulse, it breaks the machine, and a tool that people fear to configure is abandoned. For that reason five bundle ids can never be blocked or limited, and they are listed in `PROTECTED_BUNDLE_IDS` in `focus-core`. They are Grumpo itself, Finder, the login window, System Settings and the Dock.

Each has a concrete failure behind it. Grumpo is the only interface through which an unlock can be requested and confirmed, so a rule that quits Grumpo would lock the person out of the very escape hatch that makes strict blocking tolerable. Finder and the Dock make up the desktop, and the login window owns the session, so quitting any of them repeatedly would leave the Mac close to unusable for as long as the rule held. System Settings is where the permissions Grumpo depends on are granted and where a login item is removed, so blocking it would stop the person from repairing Grumpo. Terminal is left out on purpose, because many people do want to block it, and its absence from the list is a decision and not an oversight. The reasoning is in [ADR 0008](adr/0008-protected-apps-can-never-be-blocked.md).

The protection sits in several places so that no single layer has to be perfect. The daemon rejects a rule set that names a protected app, as a blocked app or as the target of a limit, with `rules_invalid` and a sentence that names the app. The first state migration removes protected apps from saved rules, since a single old entry would otherwise make the whole saved state fail validation. The app leaves protected apps and itself out of the picker that lists apps to block, and the enforcement policy checks `is_protected` again before it quits anything, so even a status that somehow listed one would not make Grumpo act on it.

## Limit reports and stale state

An exhausted limit travels as `ReportLimitReached { target, dailyMinutes, day }`, where `dailyMinutes` is the allowance that was in force when the usage ran out and `day` is the local date on which the reporter counted it. The daemon records the target only while the report is for its own current day and the current rules still contain a limit for it that is not higher than that number. A report that names another day, a target with no limit, or one whose limit has since been raised is ignored and logged at debug level, and the reply is still the current status, so a person who edits a limit while the app is counting never causes the reporter to fail. The day check closes a race at midnight, because a report that left the app just before midnight and reached the daemon just after would otherwise block the whole new day for a limit that had not been touched yet. When two reports arrive for the same target on the same day the larger allowance is kept, so lowering a limit later cannot shrink what was already spent, and a target stays blocked only while its current limit is not higher than the recorded one, so raising a limit frees it, which is a loosening that the unlock rule guards.

The same care applies on the app side to stale statuses. When the last confirmation from the daemon predates the start of the local day, the app does not act on a block that rests only on a limit which ran out yesterday, because the daemon frees such targets at midnight and the app may simply not have heard yet.

## The clock

Every time based rule trusts the clock of the machine, and a person with the keys to the Mac can change it, so the daemon cannot defend against a clock set forward. It does make sure that setting the clock back gains nothing, since going back is the direction that stretches an unlock or hands out a fresh day. An unlock whose remaining time exceeds the minutes it was granted is relocked, a cooldown whose remaining time exceeds its step restarts with the full step, and a confirmation window longer than its length is dropped. The unlocks used today and the record of exhausted limits reset only when the local date moves forward, so moving the date back neither resets the escalation nor frees a spent limit. Forward changes are still accepted, as the list of bypasses says.

## The hosts block

A hosts file has no wildcards, so a block is only as wide as the names it lists. For each blocked domain the daemon writes the bare domain and the prefixes `www.`, `m.`, `mobile.`, `old.`, `new.`, `music.`, `i.` and `amp.`, each in IPv4 and IPv6, which covers the aliases that sites commonly serve the same content from. A different subdomain, such as a regional or a login host, is not covered unless the person adds it as a site of its own. The block applies to every account on the Mac, because `/etc/hosts` is shared, whereas only the owner uid can reach the daemon. Another account is therefore blocked from the listed sites without being able to change the rules or request an unlock, and its copy of the app reports the service as owned by another user. That asymmetry is deliberate, since the privileged side must not take instructions from just anyone, and it means the owner cannot lift the block for another account.

## State that cannot be loaded

The daemon distinguishes a state file that is itself at fault from a failure to read it. A file with damaged JSON, with no schema version, or whose rules no longer validate is unusable whatever the daemon does, so it is moved aside as `state.json.corrupt-<unix ts>` and the daemon starts from defaults, because the alternative is a restart loop that enforces nothing. A read error, which is an `Io` failure, and a file written by a newer daemon, which is `UnsupportedVersion`, say nothing against the file, so the daemon exits with an error and leaves it alone. Starting from defaults there would rewrite the hosts file to an empty block and end enforcement, and on a downgrade it would throw away rules that a newer daemon could read. With the exit, launchd retries under `KeepAlive`, the hosts block from the last good run stays in place meanwhile, and the installer's backup of `state.json` can be restored if the cause was an upgrade.

## Version mismatch

The app and the daemon are installed and upgraded separately, so they will sometimes speak different protocol versions. The envelope makes this safe. Each side reads the version before the body and refuses to interpret a body written for another version, which stops a newer message from being misread as an older one, and the app learns which side is behind from the number. A daemon on an older version means the service needs updating, and the fix is Update service in Settings, which runs the bundled installer, or running the installer again from Terminal. A daemon on a newer version means the app is old, and the fix is to update the app.

During a mismatch the app has no status, so it enforces nothing on its own, and the commands that need the daemon fail with a clear error instead of relying on a body the other side could misread. The daemon keeps doing what it was installed to do, writing the hosts block for the schedule and the spent limits, so the website protection stays in place, but quitting apps and closing tabs pause until the versions agree. This degraded mode is accepted, because the alternative of guessing at a protocol the app does not know could change rules in ways nobody intended. It also means a person cannot use a mismatch to loosen anything, since the daemon decides every change by itself.

## Known bypasses that are accepted

Several bypasses are known and accepted because closing them would require either a different product or a threat model that includes the administrator.

- Root runs a script from the app bundle when someone presses Install service or Update service, and the bundle is writable by the user who owns it, as with any app that was dragged into `/Applications` or built locally. Grumpo is signed ad hoc, so the signature proves that the bundle was not damaged and cannot prove who built it, which means a process that already runs as the user can edit `Contents/Resources/installer/` or `Contents/MacOS/focusd` and re-sign the bundle before the person types the password, and its code then runs as root. Copying the files into a root-owned folder before use stops a change made after the copy, and it does not stop one made before. Such a process can already do whatever the user can, including replacing the app the person is about to open, and this is the trust model of other installers that ask an ordinary app for an administrator password. It is a real gap and not a theoretical one, and the planned fix is a Developer ID signature, after which the installer can require the team identifier in the signature requirement of the copied daemon and the bundle, or `SMAppService.daemon`, which makes launchd check the signature and removes the password script. [ADR 0011](adr/0011-app-installs-the-service-through-the-admin-prompt.md) expects that change. Until then ad hoc builds are for development and for people who accept this.
- Anyone with `sudo` can stop or unload the daemon, edit `/etc/hosts`, delete the state file or uninstall Grumpo.
- Setting the system clock forward can shorten a cooldown or reach a local midnight early, which resets the daily unlock count and clears the spent limits, because time comes from the machine. Setting it back is handled, as the section on the clock describes.
- Browsers with DNS over HTTPS enabled, or with a custom resolver or a VPN, may not consult `/etc/hosts` for some or all lookups, so a blocked site can still load in them. The tracker still records the time and the app can still close the tab in supported browsers, which limits the effect without eliminating it.
- Browsers outside the supported set (Chrome, Brave, Edge, Safari and best effort Firefox) are tracked per application only, so a blocked site opened in an unsupported browser is not closed and relies on the hosts block alone.
- Tabs are closed only in the frontmost window of Chrome, Brave, Edge and Safari, and Firefox tabs are never closed. A blocked page that is already loaded in a background window keeps running until that window comes forward, because the hosts block stops new lookups and not existing connections.
- A blocked app is quit with a polite request, which an app can decline, for instance while it shows an unsaved-changes dialog. A blocked app that starts in the background is found by a sweep that repeats every 30 seconds, so it can run for up to half a minute, and the sweep covers applications that appear in the Dock and not background-only agents.
- Time in a private window counts toward a daily limit only in memory, so quitting Grumpo erases the progress that private browsing made toward a limit that has not been reached yet. A limit that was already reached stays recorded by the daemon. Private windows in Safari and Firefox cannot be detected at all, and are counted and stored like any other browsing.
- The usage database belongs to the user, so deleting or editing `focus.db` resets the progress toward every limit that has not been reached yet. The daemon cannot check it, because the usage is stored in the app and not in the privileged side. A limit that was already reached stays blocked until midnight, since the daemon holds that record, and anyone who can replace the file already controls the account, which is the impulsive self that the design only slows down. If the app finds the file damaged it starts a new one the same way, keeps the old file as `focus.db.corrupt-<unix ts>` and tells the person.
- A site installed as a web app, such as a Chrome or Edge app or a Safari web app in the Dock, runs as an app of its own with its own bundle id, so its time counts under that app and not under the site, and Grumpo cannot close it as a tab. A site limit does not reach it. Blocking the wrapper as an app in the Rules screen covers it, while the hosts block keeps applying to the site itself. Grumpo does not map wrappers to their sites.
- A subdomain outside the alias list of the hosts block is not blocked by it, and a person can use that until they add the subdomain as a site.
- A person can quit the app or disable launch at login, which stops tracking and the closing of tabs and apps, although the hosts block continues to be enforced by the daemon while a window or limit is active. The tray warns about this, since its quit item reads "Quit Grumpo (stops app and tab blocking)" while blocking is active.
- Terminal is not protected, so a rule that blocks it can be avoided with any other terminal program that is not blocked, and the same holds for any app that has a substitute.

These choices are honest limits of a user-space focus tool, and the documentation states them so that nobody mistakes Grumpo for an access control system.
